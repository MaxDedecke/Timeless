# Design-Rückblick auf Sprint 5

Sprint 5 rundet das Sprintziel sauber ab: Die Buchung lässt sich aus dem Raumkalender mit sichtbarer Konflikt-Rückmeldung anlegen, Check-in/No-Show sind konzeptuell vorbereitet und tabular-nums ist inzwischen durchgängig per Test abgesichert – das Gesamtbild wirkt reif. Uneinheitlich ist derzeit die Formulararchitektur: Die Raumverwaltung läuft über eigene Routen (/rooms/new, /rooms/:id/edit), die Buchung dagegen über einen Dialog – beides ist einzeln nachvollziehbar, aber ohne dokumentierte Regel entscheidet jedes kommende Formular (Serienbearbeitung, Gäste, Genehmigungen) das Paradigma neu. Zudem sollte BookingForm einmal explizit am dokumentierten Zustands-Muster (Submit-Ladezustand, Server-Fehleranzeige) gespiegelt werden. Für den nächsten Sprint liegt die Freie-Räume-API fertig da, ohne dass ein UI-Muster dafür steht – Filter-, Ergebnis- und Leerzustand sollten vorab im Konzept festgelegt werden. Schließlich fehlt für die Zeitraster (TimeGrid, Tagesansicht) noch eine Aussage zum Verhalten auf schmalen Breiten, obwohl der Design-Standard Mobile-Funktion verlangt.
